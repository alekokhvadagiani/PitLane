## Access and data policy

- OpenF1's reviewed documentation does not establish a numeric rate quota. A direct request on 2026-10-26 returned HTTP 429 with `Max 3 requests/second`; PitLane now spaces upstream requests by 450ms and observes `Retry-After` when present. Treat the observed limit as changeable, and keep bounded concurrency, caching, and small time windows. Confirm current subscription transport/authentication when implementing live.
- Use UTC instants, not local wall-clock strings. Check session origins and radio timestamp meaning against actual responses. Driver numbers and provider IDs are not globally interchangeable.
- Missing telemetry is null/unavailable; avoid interpolation across long gaps or comparing unaligned lap samples. Location is provider-local coordinates, not automatically GPS or authoritative track geometry.
- Radio URLs do not establish playback/republication rights. Before audio integration, review applicable upstream terms, expose only available clips, handle removed/expired URLs and browser playback errors, avoid autoplay, and do not download or redistribute a radio archive by default.
- Historical cache should be bounded and keyed by provider, session, stream, version and window. Report stale/partial data; failures must never become fake success.

## Historical catalog integration

The OpenF1 meetings and sessions catalog is integrated behind `IHistoricalSessionProvider`. Requests are bounded to one season or meeting, cached in memory for 30 minutes, and report `source` and `retrievedAtUtc`. The UI exposes the catalog and keeps selected year/meeting/session in the URL. A real OpenF1 meeting catalog response was observed during implementation. This proves catalog access only, not replay-stream coverage. A numeric OpenF1 quota remains undocumented in the reviewed materials.

OpenF1 documents weather at roughly one-minute intervals, with UTC `date`, air/track temperature, humidity, pressure, binary rainfall, wind speed, and wind direction. PitLane exposes these observations at `/api/sessions/{sessionKey}/weather` and in the selected-session Replay view. Missing observations/fields remain explicit. A real request for the 2025 Australian GP race (session 9693) returned 178 observations from 03:07 to 06:04 UTC; this is one sample session, not a coverage guarantee. See [OpenF1 weather documentation](https://openf1.org/docs/#weather).

The same 2025 Australian GP session returned 928 lap records. A single car's full location query returned 39,559 rows; a one-minute UTC window for driver 1 returned 221 rows. Replay position requests should therefore be scoped by driver and time window. These counts describe the sampled session only. See [OpenF1 car location](https://openf1.org/docs/#location) and [laps](https://openf1.org/docs/#laps).

During the 2026-10-26 replay investigation, session 11416 resolved to 2026 Las Vegas qualifying on 2026-11-21, which had not yet occurred. Its driver roster endpoint returned data, while weather and position endpoints returned HTTP 404 with `{"detail":"No results found."}`. This confirms that meeting/session metadata (and even a roster) does not guarantee replay streams. The adapter now treats that exact no-results response as an empty catalog. Other upstream failures remain errors; HTTP 429 responses include the retry delay when supplied.

## Next validation

Continue validating full-session replay and sample position/lap coverage across additional sessions and drivers. The current trace shows OpenF1 local coordinates; do not describe it as surveyed circuit geometry. Full-session single-driver location payloads are large enough to require bounded windows. Live integration, telemetry comparison, and radio playback remain unimplemented.

## Tyre and driver-state feeds (2026-10-26)

Reviewed the official [OpenF1 endpoint documentation](https://openf1.org/docs/) for `laps`, `stints`, `pit`, and `session_result`. Stints include compound, stint number, lap start/end, and tyre age. Pit rows include an event date and total lane duration. Session results include final DNF/DNS/DSQ flags, but not the point in time when a car retired. Direct OpenF1 requests for session 11396 returned 1,166 lap rows, 54 stints, 32 pit rows, and 22 result rows.

Pit status has an important limit: the docs describe `date` as UTC date/time and `lane_duration` as time in pit lane, but do not define whether `date` marks pit entry or pit exit. PitLane therefore displays an explicitly estimated interval and should not represent it as exact timing. DNF/DNS/DSQ are displayed as final result badges; current playhead state remains based on recent location observations. `ON TRACK` means a location sample no more than two seconds old; missing/stale coordinates show `NO DATA`. New cached API routes serve all session laps, stints, pits, and final results. These backend changes compile but still require an API restart and runtime check.
